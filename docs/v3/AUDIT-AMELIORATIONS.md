# PLAN D'AMÉLIORATION PRIORISÉ — MEMORIA V3

Note transverse : un cas se répète dans 3 audits (cognition, recall, gouvernance) — **le filtre `length > 2` / nombres-bruts dans `content.ts` (queryTokens / significantTokens)** pollue à la fois les labels, le recall et l'effacement RGPD. C'est le plus gros ratio impact/effort de tout le lot.

## 1. TOP 5 QUICK WINS (fort impact / effort raisonnable)

### QW1 — Durcir la redaction des secrets et la déplacer dans `storeFact`
- **Quoi** : (a) brancher le redactor sur `storeFact` (pas seulement la CapturePipeline) ; (b) ajouter les patterns manquants (Stripe `sk/rk/pk_(live|test)_…`, `whsec_`, Google OAuth `ya29.`, Azure SAS, Bearer headers, connection strings `proto://user:pass@`).
- **Pourquoi** : trou de sécurité direct. Aujourd'hui un agent qui POST `{content:"sk-ant-…"}` via `/store_fact`, ou tout import legacy/transcript, écrit le secret **en clair** dans `facts/.md`/projection — alors que le code promet « jamais ». Et même la pipeline laisse passer Stripe (`cs_live_`/`sk_live_`), pertinent vu l'écosystème Primo.
- **Comment** : redaction dans `storeFact` avant `insertFact` (flag interne `skipRedaction=false`), même `secretProvider` que la pipeline ; passer chaque fact legacy/transcript par le redactor ; étendre `redaction.ts:25-54`. Documenter « best-effort, défense en profondeur ».
- **Effort** : rapide-moyen (1 point d'entrée + ~6 regex + tests).

### QW2 — Sécuriser le daemon HTTP (timing-safe + anti-DNS-rebinding + token 600 atomique)
- **Quoi** : (a) `crypto.timingSafeEqual` pour le token admin (comparer longueurs hors timing) ; (b) rejeter tout `Host`/`Origin` non-loopback ; (c) `writeFileSync(p, data, {mode:0o600})` au lieu de write-puis-chmod sur `daemon.json`.
- **Pourquoi** : trois failles à coût quasi nul. La comparaison `token !== adminToken` est exploitable par timing ; sans contrôle Host/Origin un site web malveillant peut faire du DNS-rebinding vers `127.0.0.1` et lire/écrire la mémoire ; le TOCTOU expose l'`admin_token` en 644 entre write et chmod.
- **Comment** : `server.ts:101`, guard Host/Origin en début de handler (+ `Vary: Origin`), `state.ts:30-34` mode passé directement (idéalement tmp+rename atomique).
- **Effort** : rapide.

### QW3 — Filtre commun `isContentWord` (nombres/hex/tokens courts) sur labels + tokens
- **Quoi** : extraire un util partagé qui rejette `^\d+$`, hex courts, tokens >40% chiffres ; l'appliquer à `significantTokens` / `clusterKeywords` / `topicKeywords` / `observationSubject`.
- **Pourquoi** : labels illisibles aujourd'hui (« 20b 255 analyse configuration », « DE ES PGDATA »). Un util unique corrige patterns, clusters ET thèmes d'un coup, et améliore la lisibilité perçue du produit immédiatement.
- **Comment** : `patterns.ts:462-472`, `clusters.ts:116-121`, `topics.ts` keywords, `index.ts:213-222`. Au passage, durcir `heuristicEntities` (`entities.ts:144-149`) : ALLCAPS ≥3, blacklist fragments de chemin (`Users/Documents/Downloads/Library/Volumes`), appliquer `isFileLike` AVANT extraction.
- **Effort** : rapide-moyen.

### QW4 — Plafonner le boost contextuel et le découpler de `relevance_weight`
- **Quoi** : borner le produit projet×client×org (~×2.0 max) et ne plus y multiplier `relevance_weight` ; garantir que la pertinence reste dominante (`relevance^α × Π factor^β`, α≫β).
- **Pourquoi** : aujourd'hui un fait **peu pertinent** du bon projet (rel 0.25 → 0.82 avec boost ×5.38) bat un fait **parfaitement pertinent** mais ancien (rel 1.0 → 0.175). Le cœur du « recall » est faussé. Aggravé par le mode hybride qui change l'amplitude relative.
- **Comment** : `scoring.ts:31-51`. Ajouter un cas benchmark « hyper-pertinent hors-projet vs faiblement pertinent in-projet » avec assertion d'ordre.
- **Effort** : moyen (formule + recalibrage + 1 test).

### QW5 — Fixer le effacement RGPD `forget()` (faux « deleted:0 ») + token courts discriminants
- **Quoi** : (a) `forget(query)` ne doit pas troncher en silence (boucler par lots jusqu'à épuisement, remonter candidats-vs-cap, mode LIKE/substring complémentaire) ; (b) conserver les tokens courts qui contiennent un chiffre/casse mixte (`X`, `v2`, `S3`, `k8s`) dans `queryTokens`.
- **Pourquoi** : **deux conséquences graves d'un même `length>2`**. Côté gouvernance : `forget('IA')` retourne `{deleted:0}` → faux sentiment d'effacement (risque RGPD réel). Côté recall : « projet X » et « projet Y » produisent une requête FTS identique → désambiguïsation impossible sans contexte.
- **Comment** : `content.ts:94/98-102`, `memoria.ts:1334-1338`. Règle `length>2 || /[0-9]/.test(t) || hasMixedCase`. Indexer un champ « identifiants » (nom projet/client) en FTS.
- **Effort** : moyen.

## 2. TROIS CHANTIERS DE FOND (gros effort / gros impact)

### CF1 — Refonte de l'algo cognitif : matching, consolidation et complexité
Trois maux liés qui font diverger les couches cognitives :
- **Sur-fragmentation** (843 thèmes / 1025 faits) : abaisser Jaccard 0.4→~0.25 + matching par chevauchement absolu (≥2 keywords), assouplir la branche entités, ajouter un job `mergeTopics` post-hoc, masquer le bruit mono-fait (`minFacts≥2`).
- **Complexité O(N²)–O(N³)** intenable au-delà de 5000 faits : index inversé token→faits (blocking), union-find (DSU) au lieu de `while(grew)`, borner/incrémentaliser `rebuild()`/`detect()`.
- **Robustesse `detect()`** : gérer la violation d'unicité de fingerprint (deux groupes convergents font planter toute la transaction et annulent les patterns valides) — `SELECT … != id` avant UPDATE ou capter `SQLITE_CONSTRAINT`→fusion.
- **Expertise** : trier par `level × log(1+evidence)` (pas `level` seul qui sature), indexer sur le topic lisible, réduire `EXPERTISE_STEP`.
- **Effort** : gros. C'est ce qui rend la « cognition » réellement exploitable et scalable.

### CF2 — Recherche globale + visualisation de la mémoire (l'UX qui « vend » le produit)
- **Recherche globale** ⌘K/Ctrl+K interrogeant faits+thèmes+procédures de **tous** les agents (aujourd'hui cloisonnée à un agent dans l'écran Mémoire). C'est le geste #1 attendu d'un produit « mémoire ».
- **Vraie visualisation** : la couche 13 (graphe) et 16 (clusters) existent côté données mais l'UI n'affiche qu'un compteur. Ajouter une « Carte de la mémoire » (graphe de force ou frise chronologique par thème) — la fonctionnalité démo qui rend la puissance tangible.
- En parallèle, relier les 13 écrans en silos (prop `onNavigate`) et regrouper la nav en 3 sections + pastilles de compteur sur Revue/Récurrences.
- **Effort** : gros (nouvel endpoint d'agrégation + 2 composants), mais c'est le plus fort levier de compréhension/adoption.

### CF3 — Cohérence du graphe cognitif au hard-delete + isolation client robuste
- **Hard-delete « partout »** : centraliser TOUT le nettoyage dans `hardDeleteFacts` (point de passage unique de forget/reviewDecision/shareFacts/rollbackImport) : `fact_entities`, relations/decay, `cluster_members`, `revision_proposals`, `self_observations`, recompute observations. Aujourd'hui des orphelins gonflent les compteurs de co-occurrence et laissent des `revision_proposals` pointant vers des `fact_id` morts. Test : suppression → 0 ligne résiduelle dans les 8 tables.
- **Isolation client** : dériver l'isolation aussi via `project_id→client` (pas seulement `client_org_id` qui est souvent null), pour fermer la fuite par expansion graphe d'un fait projet sans client_org_id vers un autre client.
- **Partage sûr** : `shareFacts` doit refuser/downgrader `sensitivity='critical'`, re-passer par le redactor, vérifier `can_share`, et copier une **whitelist** de colonnes (pas `pragma table_info`).
- **Effort** : gros (touche conformité RGPD + sécurité multi-tenant, à tester sérieusement).

## Détail des findings par domaine


### Qualité cognitive (topics / patterns / clusters / expertise / observations / self-observation / revision)

- **[majeur/moyen] Sur-fragmentation des thèmes : seuils de matching trop durs + filtre entités trop agressif → 1 thème par fait**
  - Preuve : topics.ts:127-165 (assignFact). Un fait ne rejoint un thème existant que si (a) ≥2 entités partagées OU ≥1 entité forte person/company/project (l.147), OU (b) Jaccard de keywords > 0.4 (l.162). Or entitiesOf() (l.108-116) jette toutes les entités fichier/chemin via isFileLike (l.317-319), et l'extraction heuristique produit surtout 0-1 entité par fait. Résultat : la branche entités échoue presque toujours et il reste un Jaccard > 0.4 sur des keywords courts (>3 car.), bar quasi inatteignable pour des faits d'1-2 phrases. C'est exactement le symptôme observé : claude-code = 843 thèmes pour 1025 faits.
  - Amélioration : 1) Abaisser le seuil Jaccard keyword de 0.4 à ~0.25 et ajouter un matching par CHEVAUCHEMENT ABSOLU (≥2 keyword en commun) en plus du ratio, pour les faits courts. 2) Assouplir la branche entités : ≥1 entité forte suffit déjà, mais autoriser aussi ≥1 entité partagée tout court quand le fait n'a qu'une entité (sinon impossible d'atteindre 2). 3) Ajouter un job de consolidation post-hoc : fusionner les thèmes dont les ensembles de keywords/entités se recouvrent (mergeTopics) et plafonner par défaut listTopics à minFacts≥2 dans l'UI pour cacher le bruit mono-fait.

- **[majeur/moyen] Libellés de thèmes bruités car l'heuristique colle des entités-déchets et le LLM n'est presque jamais déclenché**
  - Preuve : heuristicLabel (topics.ts:214-222) concatène les 2 entités de plus haut rang de type → « DaVinci PGDATA », « DE ES ». La source du bruit est entities.ts:heuristicEntities : l.144-145 capture TOUT ALLCAPS de 2+ lettres comme 'concept' (« DE », « ES », « PGDATA »), l.149 capture toute séquence capitalisée (« Users Documents » vient d'un chemin /Users/.../Documents). Et le garde-fou LLM ne se déclenche QUE si label.split(' ').length < 2 (topics.ts:186) : un libellé à 2 mots, même absurde, ne passe JAMAIS par le LLM de nettoyage.
  - Amélioration : 1) Dans entities.ts, exiger ALLCAPS de longueur ≥3 et une liste noire de fragments de chemins (Users, Documents, Downloads, Library, Volumes…) ; appliquer isFileLike AVANT extraction, pas seulement au moment du label. 2) Remplacer la condition LLM `< 2 mots` par un score de QUALITÉ du label heuristique (rejet si tokens ALLCAPS isolés, mots <3 car., ou fragments de chemin) → déclencher le LLM quand le label est suspect même à 2+ mots. 3) Filtrer les entités de type 'concept' issues de l'ALLCAPS hors d'une whitelist (NAS, QNAP, API…) avant de bâtir le label.

- **[majeur/rapide] Labels de patterns illisibles : nombres/hex/tokens techniques pris pour des mots-clés thématiques**
  - Preuve : labelFor (patterns.ts:568-580) prend les tokens les plus fréquents du groupe via significantTokens (l.462-472), qui ne filtre QUE par longueur ≥3 et stopwords — jamais les nombres ni les chaînes alphanumériques. D'où « 20b 255 analyse configuration » : « 20b » (hex/identifiant) et « 255 » remontent comme keywords dominants. Même défaut dans clusters.ts:clusterKeywords (l.116-121) et dans observationSubject (index.ts:213-222) qui garde les 3 premiers mots >3 car. bruts.
  - Amélioration : Ajouter dans significantTokens / clusterKeywords / topicKeywords un filtre commun : rejeter les tokens purement numériques (/^\d+$/), les hex courts (/^[0-9a-f]{1,8}$/ quand contient un chiffre), et les tokens contenant >40% de chiffres. Idéalement extraire ce filtre dans un util partagé (isContentWord) réutilisé par topics/patterns/clusters pour cohérence.

- **[majeur/moyen] Expertise triée par 'level' saturant : l'ordre ne reflète ni le volume ni l'importance réelle du domaine**
  - Preuve : topDomains (feedback.ts:300-310) trie par level DESC, evidence_count DESC, domain ASC. Mais updateExpertise (l.274) sature très vite : next = prev + delta*(1-prev) avec EXPERTISE_STEP=0.15 → 3-4 signaux suffisent à dépasser 0.5, et après ~6 signaux quasiment tous les domaines actifs convergent vers ~0.8-0.9. Le 'level' devient peu discriminant ⇒ l'ordre effectif retombe sur evidence_count puis alphabétique. De plus le 'domain' = fact.category brute (reinforce l.201 domainHits sur r.category), donc des domaines comme « savoir »/« preference » dominent au lieu de thèmes lisibles.
  - Amélioration : 1) Trier topDomains par un score combiné level × log(1+evidence_count) (ou Wilson lower-bound sur utiles/total) plutôt que level seul, pour que le volume départage. 2) Indexer l'expertise sur le TOPIC lisible (ou category+topic) plutôt que la category brute, pour des domaines parlants. 3) Réduire EXPERTISE_STEP (~0.08) ou rendre la saturation dépendante du volume, pour garder du contraste entre domaines.

- **[majeur/gros] Clustering et détection de patterns en O(N²) (voire O(N³)) — non tenable sur 5000+ faits**
  - Preuve : clusterCandidates (patterns.ts:512-536) et connectedComponents (clusters.ts:325-347) ont une boucle `while(grew)` qui, à chaque croissance, re-balaye TOUS les candidats et teste similar() contre TOUS les membres du groupe → pire cas O(N² · tailleGroupe), proche de O(N³) pour un gros cluster. rebuild() (clusters.ts:154) recharge et repartitionne l'INTÉGRALITÉ des faits actifs à chaque appel, sans borne. Sur 5000 faits actifs ça représente des dizaines de millions de calculs de Jaccard à chaque rebuild/detect.
  - Amélioration : 1) Construire un index inversé token→faits et ne comparer que les paires partageant au moins un token rare (blocking / candidate generation) au lieu du produit cartésien. 2) Utiliser une union-find (DSU) sur les arêtes pré-calculées au lieu du while(grew) ré-balayant tout. 3) Borner rebuild()/detect() (limite de faits, fenêtre temporelle) ou les exécuter en incrémental. À documenter comme limite connue si non corrigé.

- **[majeur/moyen] Réconciliation des patterns fragile : risque de violation d'unicité sur l'empreinte des membres**
  - Preuve : L'index UNIQUE idx_patterns_fingerprint porte sur member_fact_ids (patterns.ts:67). findOverlapping (l.427-437) retourne le PREMIER pattern dont les membres recouvrent à >0.5, puis upsertPattern (l.401-409) fait UPDATE … SET member_fact_ids = <nouveau fingerprint>. Si un AUTRE pattern possède déjà exactement ce fingerprint (deux groupes voisins qui convergent vers le même ensemble entre deux runs), l'UPDATE viole la contrainte UNIQUE → exception non gérée qui fait planter toute la transaction detect() (l.197-206), annulant aussi les patterns valides du même run.
  - Amélioration : Avant l'UPDATE de fingerprint, vérifier qu'aucun autre pattern ne porte déjà cette empreinte (SELECT … WHERE member_fact_ids = ? AND id != ?), et le cas échéant fusionner/supprimer le doublon au lieu d'écraser. Ou capturer SQLITE_CONSTRAINT et router vers une fusion. Tester explicitement le scénario 'deux groupes convergent vers le même ensemble de membres'.

- **[mineur/moyen] Faits 'fichier-only' silencieusement exclus des thèmes → faits orphelins re-scannés à chaque assignPending**
  - Preuve : entitiesOf (topics.ts:108-116) retire les entités fichier/chemin ; si un fait ne contient QUE des entités fichier (ex. « config dans /Users/.../config.env ») et < 4 keywords utiles, il peut atterrir dans createTopic avec heuristicLabel='Divers' (l.221) ou un thème keyword pauvre. Surtout, assignFact crée TOUJOURS un topic (l.168) donc un fait sans signal exploitable reçoit un thème de qualité nulle, et assignPending (l.249-264) ne marque rien : tout fait sans fact_topics est re-tenté à chaque passe (ici toujours assigné, mais un fait au texte vide sortirait en {created:false} sans lien, donc re-scanné indéfiniment à chaque boot).
  - Amélioration : 1) Pour les faits sans entité non-fichier ET sans keyword suffisant, soit les ranger dans un thème générique unique 'Fichiers/Chemins', soit conserver les entités fichier mais avec un poids réduit plutôt que les jeter. 2) Marquer les faits inclassables (table de garde ou topic 'Non classé') pour qu'assignPending ne les re-scanne pas en boucle. 3) Garde explicite : si fact.fact.trim() est vide après normalisation, ne pas créer de topic et logguer.

- **[mineur/moyen] Observations agrégées sur une clé grossière (catégorie + 3 premiers mots) → collisions et écrasement de contenu**
  - Preuve : observationSubject (index.ts:213-222) = category + 3 premiers mots >3 car. du fait. upsertObservation (observations.ts:52-59) fait, sur clé existante, content = ? (écrase) — donc deux faits différents qui commencent par les mêmes 3 mots dans la même catégorie écrasent mutuellement leur 'content', ne gardant que le dernier. Ex. « Déploiement Vercel échoue… » et « Déploiement Vercel réussi… » → même subject 'savoir: deploiement vercel echoue/reussi'? non : 3 premiers mots identiques 'deploiement vercel echoue' vs 'deploiement vercel reussi' divergent au 3e — mais beaucoup de faits partagent réellement les 3 premiers mots et perdent leur contenu.
  - Amélioration : 1) Construire la clé sur les mots SIGNIFIANTS triés (pas les 3 premiers positionnels) ou sur les entités dominantes, pas l'ordre de surface. 2) Plutôt qu'écraser content, conserver une synthèse incrémentale (concaténation bornée / liste de fact_ids contributeurs) pour ne pas perdre l'information des faits agrégés.

- **[mineur/rapide] deriveFromHistory (self-observation) : confiance d'habitude non bornée par le bon facteur et formulation figée par occurrences**
  - Preuve : self-observation.ts:353 : confidence d'une 'habit' = clamp01(0.4 + 0.1*occurrences). Dès 6 occurrences la confiance sature à 1.0 (plafond clamp), ce qui surreprésente des récurrences faibles. Contrairement aux 'strength/weakness' qui passent par volumeFactor (l.326-336), l'habit n'utilise PAS volumeFactor → incohérence de calibrage entre kinds. De plus l'observation inclut le nombre d'occurrences dans le TEXTE (« … (8 occurrences) », l.356), donc norm_key change quand le compteur change → l'UPSERT par norm_key (l.211-213) NE dédupe PAS : chaque variation d'occurrences crée une NOUVELLE self-observation au lieu de renforcer l'existante.
  - Amélioration : 1) Aligner l'habit sur volumeFactor (confidence = base * volumeFactor(occurrences)) pour un calibrage cohérent et non saturant. 2) Sortir le compteur d'occurrences du texte normalisé : le mettre dans evidence_count (déjà géré par l'UPSERT) et garder l'observation stable (« Habitude récurrente : <description> »), sinon la dédup par norm_key est cassée et la table croît.

- **[mineur/moyen] Détection de doublons en révision : clé exacte sur texte normalisé → rate les quasi-doublons et la reformulation**
  - Preuve : revision.ts:212-229 : dupKey = scope_id + normalizeText(fact).trim(), et la détection de doublon exige une ÉGALITÉ EXACTE de cette chaîne (seenDuplicateText.get(dupKey)). normalizeText (content.ts:105-110) ne fait que minuscules + suppression de diacritiques : la moindre différence de ponctuation, d'espace ou de mot (« préfère Vercel » vs « préfère Vercel pour le déploiement ») échappe à la dédup. La couche se prive du Jaccard déjà disponible (patterns/clusters) pour ne capturer que des copies au caractère près.
  - Amélioration : Compléter la détection 'duplicate' par un seuil de similarité (Jaccard de significantTokens > ~0.85, ou égalité après suppression ponctuation/espaces multiples) en plus de l'égalité exacte, en réutilisant significantTokens/jaccardSets de patterns.ts. Garder l'égalité exacte comme cas rapide.

- **[cosmétique/rapide] Recompute d'importance des thèmes ne se déclenche jamais en arrière-plan → scores de récence périmés**
  - Preuve : topics.ts:225-246 recompute() calcule importance = count*(0.5+0.5*recency) avec recency dépendant de l'âge du dernier fait (l.237-239). Mais recompute n'est appelé QUE lors d'assignFact ou onForget (l.177, 304). ### Qualité du recall &amp; scoring (Memoria V3, branche memoria-v1)

- **[majeur/moyen] Le boost de contexte écrase la pertinence : un fait peu pertinent du bon projet bat un fait parfaitement pertinent**
  - Preuve : scoring.ts:43-51 — `total = relevance × … × boost`, où `boost = 1.6(projet)×1.4(client)×1.2(org) × relevance_weight(≤2.0)`, soit jusqu'à ×5.38. `relevance` est borné [0,1]. Simulation : fait rel=0.25 frais+chaud+boost projet = 0.82 ; fait rel=1.0 vieux 180j = 0.175 → le second (parfaitement pertinent) est enterré. Le boost est multiplicatif et non plafonné face à une pertinence qui, elle, sature à 1.
  - Amélioration : Borner le boost (ex. plafonner le produit projet/client/org à ~2.0) ET le découpler de relevance_weight (qui devrait modérer l'usage, pas le contexte). Mieux : passer en score additif pondéré sur facteurs normalisés `Σ wᵢ·log(factorᵢ)` ou `relevance^α × Π factor^βᵢ` avec α≫β pour garantir que la pertinence reste le facteur dominant. Ajouter au benchmark un cas « fait hyper-pertinent hors-projet vs fait faiblement pertinent dans-projet » avec assertion sur l'ordre.

- **[majeur/moyen] Les tokens courts (≤2 car.) sont jetés : « projet X » et « projet Y » produisent une requête FTS identique — la désambiguïsation repose entièrement sur le boost**
  - Preuve : content.ts:94 `filter(t => t.length > 2)`. Vérifié : queryTokens('commande de build du projet X') = ['commande','build','projet'] = queryTokens('...projet Y'). Les identifiants discriminants X/Y/A/B/v2 sont supprimés. Dans benchmark.test.ts:81-99 le top-1 « make release-x » en contexte X n'est correct QUE grâce au boost 1.6 ; à pertinence FTS égale, retirer le contexte casserait la distinction. Un agent qui interroge sans active_context ne peut pas séparer les deux projets.
  - Amélioration : Conserver les tokens alphanumériques courts qui contiennent un chiffre ou sont en casse mixte (X, Y, v2, S3, k8s), via une règle `length>2 || /[0-9]/.test(t) || hasMixedCase`. Indexer aussi en FTS un champ « identifiants » (nom projet/client) joint au fait. Ajouter un cas benchmark : même requête sans active_context doit quand même classer la bonne procédure via le token discriminant.

- **[majeur/moyen] La fusion RRF mélange deux échelles incompatibles : FTS passe son `relevance` réel, le vectoriel passe un score RRF — fusion incohérente**
  - Preuve : hybrid.ts:21-72. Quand le vecteur est absent ou l'extension vec indisponible (cas par défaut, embeddings optionnels), `hybridSearchFacts` retourne `ftsHits` tels quels → `relevance` = couverture×bm25 (échelle 0..1 ~0.2-1.0). Quand le vecteur est présent, TOUS les hits (y compris ceux trouvés par FTS) voient leur `relevance` réécrite en score RRF `(k/2)/(k+rang+1)` ≈ 0.0082-0.5 (hybrid.ts:56,72). Le même hit FTS top-1 passe donc de relevance≈0.9 à ≈0.49 selon que les embeddings sont activés ou non. Comme ce `relevance` est ensuite multiplié par récence/confiance/boost dans scoreFact, l'activation des embeddings change silencieusement l'amplitude relative pertinence-vs-contexte (le boost pèse 2× plus lourd en mode hybride).
  - Amélioration : Normaliser la sortie hybride sur la même échelle que le FTS pur (ex. min-max sur le batch, ou conserver la couverture FTS comme plancher de relevance et n'utiliser le RRF que pour le rang). Documenter et tester l'invariant « activer les embeddings ne dégrade pas le classement FTS pur ». Ajouter au benchmark un run en mode hybride (provider d'embeddings factice déterministe) comparé au mode FTS.

- **[majeur/moyen] Plafond dur de 50 hits par DB AVANT scoring : des résultats pertinents sont coupés par bm25 brut avant que récence/confiance/boost ne s'appliquent**
  - Preuve : memoria.ts:319-324 `search(store, query, { limit: 50, … })`. searchFacts (content.ts:231-234) trie par `bm25` puis `LIMIT 50`. Le scoring global (récence/boost/hot/lifecycle) n'est appliqué QU'APRÈS (memoria.ts:329), donc un fait du projet actif très récent mais 51ᵉ en bm25 brut n'atteint jamais le scoring et est perdu. Avec un seul terme fréquent (« projet », « build ») dans une grosse DB, 50 est vite atteint. Le boost contextuel — supposé prioriser — ne peut pas rattraper un fait déjà éliminé au pré-tri SQL.
  - Amélioration : Soit récupérer un candidat-set plus large (ex. limit = max(200, k×10)) avant scoring, soit pré-filtrer en SQL les faits du contexte actif (project_id/client_org_id du contexte) en plus du top-bm25 (UNION), pour garantir qu'aucun fait in-context n'est coupé au pré-tri. Mesurer le recall@k avec/sans ce cap sur un jeu de 500+ faits.

- **[majeur/rapide] Aucune déduplication par contenu lors du fan-out multi-DB : un fait partagé (shared) peut apparaître deux fois et consommer deux fois le budget tokens**
  - Preuve : memoria.ts:317-345 boucle sur `searchTargets` (plusieurs DB : privée + shared user/org/client). La dédup `existing` (memoria.ts:350,366) n'existe QUE pour l'expansion graphe et se base sur `item.id`. shareFacts (memoria.ts:1195-1209) fait `INSERT OR IGNORE` puis `hardDeleteFacts` de la source → normalement l'id est unique. MAIS adoptLegacyInto (memoria.ts:1117-1129) ré-insère les faits legacy dans la DB privée avec leur id d'origine via `INSERT OR IGNORE`, sans garantie d'unicité globale entre une copie déjà partagée et la copie adoptée ; et importCognition/import multiples peuvent recréer des contenus identiques sous des id différents. Le candidate-set (memoria.ts:331) n'a aucune dédup par hash de contenu → deux faits au texte identique (même fait re-capturé, ou présent en privé ET en user après un partage incomplet) occupent deux slots et doublent le coût tokens.
  - Amélioration : Dédupliquer le candidate-set par hash de contenu normalisé (ou par id) AVANT le tri/cap, en gardant le meilleur score. Vérifier qu'un fait présent dans plusieurs scopes lisibles n'est compté qu'une fois. Ajouter un cas benchmark : même contenu en scope privé et user → une seule occurrence dans le recall.

- **[mineur/rapide] Le facteur `usage` est quasi-inopérant et auto-renforçant via recall_count (boucle « riche devient plus riche »)**
  - Preuve : scoring.ts:31 `usage = 1 + log1p(used_count + 0.5·recall_count)·0.15`. Plage réelle : used=0 → 1.000 ; used=50,recall=200 → 1.753 (vérifié). C'est le facteur le plus faible, dominé par récence/confiance/boost. Surtout, `recall_count` est incrémenté à CHAQUE recall qui retourne le fait (content.ts:251-255, appelé memoria.ts:412), sans signal de réelle utilité — un fait remonté par hasard grimpe en `usage` et a donc plus de chances de re-remonter : boucle de rétroaction positive non bornée par la pertinence. Le vrai signal d'utilité (`used_count` via reinforce) pèse seulement 2× plus que recall_count dans la formule.
  - Amélioration : Découpler : ne booster que sur `used_count` (usage confirmé) et utiliser `recall_count` uniquement pour le diagnostic, pas le scoring (ou avec un poids ≪). Sinon, normaliser usage par l'âge (taux d'usage) pour ne pas avantager mécaniquement les vieux faits. Ajouter un test anti-boucle : remonter 10× un fait non-pertinent ne doit pas le faire dépasser un fait pertinent jamais remonté.

- **[majeur/moyen] Expansion graphe : la relevance dérivée (≤0.2) suffit à injecter des voisins qui peuvent battre de vrais hits une fois le boost appliqué**
  - Preuve : memoria.ts:372 `scoreFact(row, Math.min(0.4, ex.score)*0.5, …)` → relevance plafonnée à 0.2. Mais le reste du scoring (récence/confiance/usage/hot/boost) est appliqué PLEINEMENT. Un voisin graphe récent, dans le projet actif (boost ×1.6-5.4) et chaud peut atteindre 0.2×rec×conf×boost ≈ 0.2×0.95×0.95×2.7 ≈ 0.49, supérieur à un hit FTS direct faiblement pertinent (rel 0.3, hors-projet) à 0.3×…×1 ≈ 0.25. L'expansion injecte donc du bruit qui remonte au-dessus de résultats directs. De plus `ex.score` (graph.ts:148 `weight×1/(hop+1)`) n'a pas de plancher de qualité : tout voisin à 2 hops partageant une entité (ex. entité « projet » très connectée) est candidat.
  - Amélioration : Appliquer aux faits d'expansion un boost contextuel ATTÉNUÉ (ou nul) et un plafond de score absolu garantissant qu'un voisin ne dépasse jamais le pire hit direct retenu. Exiger un poids de relation minimal et exclure les entités hub (degré élevé) comme ponts. Ajouter au benchmark un cas « entité hub partagée » vérifiant que l'expansion n'injecte pas >N faits non pertinents sous le cap.

- **[mineur/rapide] Le cap tokens « skip-and-continue » remplit le budget de petits faits et peut éjecter un gros fait plus pertinent**
  - Preuve : memoria.ts:397-403 : la boucle fait `continue` (pas `break`) quand un fait dépasse le budget restant. Les candidats sont triés par score, mais dès qu'un fait coûteux est sauté, des faits suivants moins pertinents mais plus courts sont admis tant que le budget tient. Résultat : à budget serré (benchmark token_budget:400, memoria.ts:158), le top-1 long peut être omis au profit de plusieurs faits courts moins pertinents. Le test bruit (benchmark.test.ts:152-161) ne le détecte que parce que « make release-x » est court ; un top-1 verbeux échouerait.
  - Amélioration : Documenter/choisir explicitement la stratégie (knapsack score/coût, ou garantir l'inclusion du top-1 même s'il dépasse, comme le fait déjà le `&& selected.length>0`). Trier par densité score/token, ou réserver le budget au top-k par score avant remplissage. Ajouter un cas benchmark avec un top-1 long (>budget partiel) qui doit rester présent.

- **[majeur/moyen] Anti-fuite : trou sur l'expansion graphe si la table fact_entities n'est pas à jour, et dépendance fragile au mapping scope→client**
  - Preuve : passesClientIsolation (scoring.ts:61-64) protège sur `client_org_id` du fait. Mais l'expansion graphe (memoria.ts:364, cognition/index.ts:175-190) borne par `allowedScopeIds` (les scopes LISIBLES), PAS par le `client_org_id` du contexte actif. Or `passesClientIsolation` est re-appliqué après (memoria.ts:369) — OK pour les faits portant un client_org_id. PROBLÈME : un fait SANS client_org_id mais sémantiquement lié au client (ex. note projet stockée en scope projet sans client_org_id renseigné — possible car storeFact:251 met `client_org_id: input ?? scope.client_org_id`, et un scope projet sans client_org_id le laisse null) passe `passesClientIsolation` (return true si null) et peut être remonté en contexte d'un AUTRE client via l'expansion si son scope est lisible. L'isolation repose entièrement sur le remplissage correct de client_org_id à l'écriture, jamais re-dérivé du project→client au recall.
  - Amélioration : Dériver l'isolation aussi via le project_id (un fait d'un projet du client A doit être masqué en contexte client B même si client_org_id est null), en réutilisant la hiérarchie projet→client déjà présente dans expandContextTree (memoria.ts:548-557) mais en sens inverse (filtrage). Ajouter au benchmark un fait de projet X SANS client_org_id explicite et vérifier fuite=0 en contexte client B.

- **[mineur/gros] Le benchmark ne couvre pas le mode hybride, la perf du fan-out, ni les cas de calibration — il valide surtout l'anti-fuite**
  - Preuve : benchmark.test.ts : 0 appel à recallSemantic (mode hybride jamais benchmarké), 0 mesure de latence/scaling (40 distracteurs seulement, 1 seul agent réel pour le recall, pas de fan-out sur N DB shared volumineuses), 0 assertion sur la calibration des facteurs (récence vs confiance vs boost), 0 cas de dédup, 0 cas d'expansion graphe bruyante. Le top-1 X/Y (l.81-99) est en réalité un test de boost, pas de pertinence (cf. tokens identiques). Les cibles « non négociables » du header (l.5-7) ne couvrent que fuite/dormant/bruit/partage.
  - Amélioration : Étendre le benchmark : (1) recall@k et MRR sur un jeu de 500-1000 faits avec ground-truth ; (2) run hybride déterministe vs FTS ; (3) micro-bench de latence du fan-out sur 5-10 DB ×10k faits ; (4) cas de calibration ciblés (chaque facteur isolé) ; (5) cas dédup et expansion-bruit listés ci-dessus. Faire échouer le CI sur régression de MRR, pas seulement sur fuite.

- **[cosmétique/rapide] Audit : forget hashe la liste TRIÉE des IDs concaténés — un audit partiellement reconstructible et non résistant à l'énumération**
